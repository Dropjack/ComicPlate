# To Learn List

To-Learn 是“你为了监督 Codex 和理解项目必须知道什么”。它不是系统学习 C# 的大课。

## 立刻要懂

### Avalonia 项目结构

你需要知道：

- `Program.cs` 是入口。
- `App.axaml` 放应用级资源。
- `MainWindow.axaml` 是主窗口 UI。
- ViewModel 保存界面状态。

够用标准：

- 你能说出“按钮在哪个文件，按钮点击后调用哪个 ViewModel 方法”。

### MVVM 最小用法

你需要知道：

- View 是界面。
- ViewModel 是状态和命令。
- Model/Core 是业务逻辑。

够用标准：

- 你能判断一段“扫描文件夹”的代码不应该写在按钮控件里面。

### 文件 IO

你需要知道：

- 如何判断路径存在。
- 如何枚举文件。
- 绝对路径和相对路径区别。
- 为什么要处理权限失败。

够用标准：

- 你能看懂“打开文件夹 -> 枚举图片 -> 排序”的代码。

### 自然排序

你需要知道：

- 字典序会把 `10.jpg` 排在 `2.jpg` 前面。
- 自然排序会按数字值比较。

够用标准：

- 你能用测试数据判断排序是否符合漫画阅读直觉。

### 只读原则

你需要知道：

- ComicPlate 可以写自己的设置、进度、日志和缓存。
- ComicPlate 不应该删除、移动、重命名、修改用户漫画文件。
- “从最近打开中移除”只删除 ComicPlate 的历史记录，不删除磁盘文件。

够用标准：

- 你能判断一个菜单项是否有修改用户文件的风险。

### 图片解码和内存释放

你需要知道：

- 图片文件可能很大。
- 图片流要释放。
- 一次加载整本书会爆内存。

够用标准：

- 你能判断“把所有图片一次性读成 Bitmap”是危险路线。

## 第二阶段要懂

### JSON 配置

你需要知道：

- 设置和历史可以保存为 JSON。
- JSON 需要版本号。
- 读失败要有默认值。

够用标准：

- 你能打开 `settings.json` 看懂每个字段。

### C# async/await

你需要知道：

- 文件扫描和图片加载可能耗时。
- UI 线程不能被长任务卡住。
- `CancellationToken` 用于取消旧任务。

够用标准：

- 你能理解为什么打开大压缩包时不应该卡死窗口。

### ZIP 读取

你需要知道：

- ZIP 里有条目，不一定都是文件。
- 条目可能在子目录里。
- 条目流需要及时关闭。

够用标准：

- 你能检查“非图片忽略、图片排序、打不开时报错”是否都处理了。

### 简单 Action

你需要知道：

- Action 是应用内部的固定操作，例如下一页、切换双页、复制路径。
- 快捷键、工具栏、右键菜单可以调用同一个 Action。
- ComicPlate 不做 NeeView 那种可编辑、可复制、可脚本扩展的复杂命令系统。

够用标准：

- 你能说清楚“右键菜单项背后调用哪个动作”，但不需要理解复杂命令框架。

## 打包前要懂

### Windows publish

你需要知道：

- Debug 运行和 Release 打包不同。
- 单文件发布、自包含发布会影响体积。

够用标准：

- 你能运行打包命令，并知道输出目录在哪里。

### macOS app bundle

你需要知道：

- macOS 应用通常是 `.app` bundle。
- 权限、签名、公证是后续问题。

够用标准：

- 你能在 macOS 上启动打包出来的应用。

### Git 分支与回滚

你需要知道：

- 每个阶段最好单独提交。
- 出错时可以看 diff。
- 不要混着改文档、架构、UI 大重构。

够用标准：

- 你能让 Codex 给你解释本次 diff 改了什么。

## 暂时不用学

现在不用学：

- WPF。
- NeeView 的完整实现。
- 插件系统。
- 脚本系统。
- 复杂命令系统。
- 主题格式。
- PDF 渲染。
- 视频播放。
- 数据库。

这些知识不但不帮 MVP，反而会把注意力带偏。

哪怕只有几行，也应该放进 PlatformService，因为它的性质不是“阅读逻辑”，而是“操作系统能力”。

比如“在资源管理器/Finder 中显示当前页”这个 Action，业务层只应该表达：

Reveal current page in file manager

它不应该知道 Windows 要调用 explorer.exe /select,xxx，macOS 要调用 open -R xxx。

更干净的链路是：

右键菜单：在文件管理器中显示
→ RevealInFileManagerCommand
→ ReaderViewModel
→ IPlatformService.RevealInFileManager(path)
→ WindowsPlatformService / MacPlatformService

这样以后你要修 macOS 的 Finder 打开方式，不会动到阅读器逻辑；要修 Windows 路径转义，也不会影响 macOS；要写测试，也可以 mock 一个假的 IPlatformService。

你可以把规则写死：

凡是和操作系统交互有关的东西，都先考虑放进 PlatformService。

包括：

打开 Finder / Explorer；
复制到剪贴板；
获取 AppData / Application Support 路径；
打开外部 URL；
显示系统文件选择器；
文件关联；
平台快捷键修饰键；
菜单栏行为；
系统主题检测。

但普通的 Path.Combine、Path.GetFileName、Directory.EnumerateFiles 这种 .NET 跨平台 API，不一定都要进 PlatformService。它们可以在 Loader/Infrastructure 里正常用。真正需要抽出来的是“不同系统行为不一样”的部分。

一句话：PlatformService 是隔离系统差异的防火墙，不是因为代码多才抽，而是因为职责不同才抽。

够用标准：

- 你能在 macOS 上启动打包出来的应用。 ””这个我不需要学吧？我可以直接在两个平台丢给vsc+codex去做就行了？

原因很简单：Codex 可以帮你写命令，但打包是最容易出现“它说成功了，但你根本不知道产物是什么”的地方。
你现在的够用标准可以压到很低：
Windows 这边你只需要知道：
开发运行通常是：
dotnet run
打 Release 包通常类似：
dotnet publish -c Release -r win-x64 --self-contained true
输出通常在：
bin/Release/netX.X/win-x64/publish/
里面会有 .exe 和一堆依赖文件；如果做单文件发布，可能主要就是一个 exe，但体积会变大。
macOS 这边你只需要知道：
macOS 用户理解的应用通常是 .app。
Debug 跑起来不等于已经有一个标准 .app。
Avalonia/.NET 可以 publish macOS 版本，但 .app bundle 结构、图标、Info.plist、权限、签名、公证是后续阶段。
你的够用目标不是“会发布给别人”，而是：
在 Windows 上能打出一个 release 文件夹，并双击启动。
在 Mac 上能打出一个可启动的 app 或至少 publish 产物，并能从 Finder/终端启动。
知道打包产物不要提交进 Git，要进 artifacts/、publish/ 或 dist/，并被 .gitignore 排除。

### 打包前要懂MVP 阶段不深入学习完整发布流程，但必须知道 Debug 运行和 Release 打包不同。Debug 运行用于开发调试，通常由 IDE 或 `dotnet run` 启动。Release 打包用于生成可分发/可双击运行的产物。Windows 需要能打出 publish 目录，并知道 `.exe` 在哪里。单文件发布和自包含发布会影响体积，自包含包更大，但目标机器不一定需要预装 .NET。macOS 应用通常是 `.app` bundle。MVP 只要求能在 macOS 上启动打包产物。签名、公证、DMG、权限声明是后续发布阶段问题。够用标准：我能让 Codex/VS Code 执行打包命令。我知道输出目录在哪里。我能在目标平台启动打包产物。我知道 publish/dist/artifacts 不应该提交进 Git。
所以答案是：可以交给 VS Code + Codex 做，但你要能验收。
尤其 Mac 这边，别等最后才打包。每做完几个核心功能，就在 Mac 上 publish 一次试启动。开发时能跑，不代表打包后路径、资源、图标、权限都正常。
